# Prax Development Workflow

1. 先读上下文，再下结论。
2. 先确认复用路径，再新增实现。
3. 先补最小可执行检查链，再扩展策略门。
4. 原生运行时能力和 Claude Code 集成能力是两类语义，禁止混用语义。

---

## 强制检查点

### 检查点 1: 创建新文件/脚本前

- 用 Grep/Glob 搜索项目中是否已有类似工具
- 检查 package.json / pyproject.toml / Cargo.toml 是否已有相关依赖
- 用户提到"项目已有 X"时，必须先去读取 X 的实现

### 检查点 2: 连续 3 次修改同一处代码

触发条件（满足任一）：
- 同一文件的同一属性被修改 3 次
- 同一问题被用户提及 3 次
- 修改值在两个值之间反复横跳

触发后动作：
1. **停止修改**
2. 输出修改历史（每轮的旧值、新值、理由、验证结果）
3. 分析根因（缺失的验证、错误的假设）
4. 向用户报告，请求新的方向或验证方法

### 检查点 3: 声明"已完成"/"已修复"前

- 提供可验证的输出（截图、测试结果、diff、量化指标）
- 不能只说"刷新浏览器看效果"、"应该通过"
- 参见 `testing.md` 中"真实结果"的定义

### 检查点 4: 遇到阻塞点 / 想偏离既定方案

触发条件（满足任一）：
- 既定方案依赖的外部条件未就绪（cert、密钥、aar、库、服务、上游接口）
- 想改用与已确认方案不同的技术路线（含"应急能跑"的兜底 / workaround）
- 要做的实现超出了用户本次明确要求的范围

触发后动作：
1. **停止实现** — 不准为了"让流程继续"而自行落地替代方案或 workaround
2. 说清楚：原方案是什么、卡在哪 / 想换成什么、为什么
3. 列出可选方向（A/B/C）及各自权衡（合规性、稳定性、落地速度）
4. 交用户拍板：继续等依赖 / 换方案 / 其他；获得明确批准后才动手
5. 默认值：拿不准就停下来问，而不是先做了再解释

禁止：
- ❌ 把"应急能跑"当作擅自实现的理由
- ❌ 既定方案被阻塞后，未经批准静默切换到备选方案
- ❌ 实现用户没要求的功能/代码，即使你认为"顺手有用"
