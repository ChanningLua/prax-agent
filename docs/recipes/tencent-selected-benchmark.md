## 共同特征

### 1. 题目大，但入口很具体

精选题影响的是架构、产品、生产流程、组织职责或行业判断。标题不会只写一个协议字段或版本变化；即使讨论宏观趋势，也会给出具体冲突，例如模型“越狱”、Agent 7×24 运行、一个工具能否完成真实设计 brief。

### 2. 大章节不多，每节都带新东西

样本通常只有 5–9 个主要章节。重量来自每章的新增信息：

- 一段完整事件链；
- 一个可复用分类框架；
- 一次真实输入与输出；
- 一个失败、修复和前后变化；
- 一张架构图、矩阵或可运行 Demo；
- 一个明确的适用与不适用判断。

如果某节只能重复观点或补充同义解释，就应该合并或删除。

### 3. 开头先让读者“看见”

事件分析用具象类比或关键现场；实测文先写为什么愿意花时间测试；框架文从作者遇到的真实讨论偏差或生产问题切入。它们不会先交代“本文背景、意义和研究方法”。

### 4. 作者必须留下工作痕迹

精选文章能看出作者做过什么：

- 逐句读过官方材料并挑出措辞；
- 实际注册、输入 brief、等待输出并检查瑕疵；
- 接过真实数据源，遇到解析、网络或交互问题；
- 画过分类矩阵或架构图；
- 对方案做过明确取舍。

仅有来源汇总、配置检查或通用清单，不足以形成作者证据。

### 5. 业务落地不是“加一节建议”

业务流程从正文一开始就存在。企业 Agent 分类文围绕网络分区、数据、身份和执行权限推进；实测文围绕真实交付物推进；事件文从攻击链反推架构控制。不存在先写八成新闻，最后补一段“企业应该重视”。

### 6. 有立场，也保留瑕疵

作者会说“这个判断不对”“这里最危险”“这个产出能直接用”，也会展示 720P、中文字距、CDN 不可达、JSONP 解析失败等问题。自然度来自真实观察和取舍，不来自刻意口语化。

## 三条写作路线

### `selected-analysis`：重大事件或行业变化

- 6,000–12,000 有效字符；
- 5–9 个 H2；
- 至少两张攻击链、时间线、对照或架构图；
- 结构：现场 → 完整事实链 → 被忽略的技术细节 → 机制解释 → 企业影响 → 可执行方案 → 边界；
- 必须有相对已有报道的新增角度，不能只改标题。

### `selected-framework`：架构、组织或决策框架

- 5,500–11,000 有效字符；
- 5–9 个 H2；
- 必须有清晰分类轴、决策矩阵和一个贯穿全文的业务场景；
- 每个分类要导致不同部署、权限、成本或责任结论；
- 框架必须能处理反例，不能只有漂亮命名。

### `selected-hands-on`：产品实测或项目实战

- 4,500–9,000 有效字符；
- 5–9 个 H2；
- 至少两个可复现的实际运行或案例；
- 至少四张真实截图、前后对照、输出或图表；
- 必须保留失败、修复、最终产物和适用人群；
- 只有安装步骤、功能清单或成功截图不能入选。

## 发布前的四道编辑门

### 撞题门

检查目标社区近 30 天的精选榜。同一事件、同一结论、同一业务落点已经有文章时，只有原创证据或判断明显更强才能继续；否则换题。

### 作者证据门

至少回答一个问题：作者亲手测试了什么、从原始材料发现了什么、画出了什么此前没有的模型、或从哪段真实业务中得到判断。

### 信息密度门

给每个 H2 标出它新增的“事实、机制、案例、产物、决策”之一。没有新增项的章节删除。连续两段不能只给原则而没有对象、动作和后果。

### 读者带走门

读完后，读者至少能带走一项可执行资产：架构图、决策矩阵、测试方法、失败清单、代码/Demo、权限模型或实施步骤。单纯“提高认知”不够。

## 对当前 OpenAI–Hugging Face 稿的结论

当前稿不进入发布：

1. 腾讯云精选榜已经有同题且更完整的事件精读；
2. 当前稿只有约 3,900 有效字符，事件链和技术机制被压得过薄；
3. “依赖升级 Agent”是参考场景，策略校验只是配置门，没有实际运行 Coding Agent；
4. 与现有精选稿相比，没有形成足够强的原创证据差。

它可保留为企业验收短稿或内部检查表，但不能作为本批次的精选校准样本。
